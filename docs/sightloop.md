# SightLoop 是什么

SightLoop 是一个**本地运行的开源「研发自愈」平台**（Business-decoupled R&D self-healing platform，MIT 许可，仓库地址 [gujiangwen/SightLoop](https://github.com/gujiangwen/SightLoop)）。

一句话概括：它把「页面上发现的一个前端问题」，变成一次**可审阅、可验证、可回滚**的代码修复，并把修复经验沉淀成知识。

## 它解决什么

前端 Bug 的修复链条通常是六步：

```text
发现问题 → 定位源码 → 修改代码 → 验证 → 评审 → 沉淀
```

其中「发现问题」发生在浏览器里，而「定位源码」需要仓库上下文、「修改代码」需要智能体和文件系统权限、「验证」需要跑命令、「评审」需要人来把关、「沉淀」需要长期记忆——这五件事无法靠一个浏览器扩展完成。

SightLoop 覆盖后五步，PinFix 覆盖第一步。

## 它由什么组成

| 部件 | 说明 |
| --- | --- |
| **本地 Agent Loop 守护进程** | Fastify 服务，默认监听 `127.0.0.1:7420`。管理项目注册、会话与步骤流水，驱动智能体执行循环（`pi` 真实模型或 `mock` 模拟），执行校验命令，用临时提交承载修改以支持回滚，并通过 WebSocket 推送实时状态 |
| **Admin 控制台** | Vite + React 界面，用于观察项目与会话、审阅 diff 与验证日志、浏览和编辑知识库、查看审计与指标 |
| **智能体运行时** | 把一次会话拆成 retrieve → act → verify → refine 的循环，负责 git 临时提交、差异计算与知识蒸馏 |
| **知识库** | 每次修复通过后沉淀为 Markdown 知识卡片，可选使用 sqlite-vec 做相似度召回，让下一次修复先「想起」过去的经验 |

可选增强包括：双循环（Planner → Implementer → Reviewer）、`gh` PR 模式、验收场景归档与回放、检查点挂起与恢复、跨模型复核。

## 它和 PinFix 的分工

| | PinFix | SightLoop |
| --- | --- | --- |
| 运行位置 | 浏览器扩展 | 本地守护进程 + Admin |
| 核心能力 | 元素定位、源码坐标、几何与文本采集、状态回显 | 智能体推理、代码修改、命令验证、人工门禁、知识沉淀 |
| 是否修改代码 | 否 | 是（在注册项目的工作区内） |
| 单独可用 | 是，提示词模式 | 否，需要问题来源 |

PinFix 早期的扩展端曾内置在 SightLoop 仓库中，现已拆分为独立项目。两者之间只保留公开协议：**PinFix 不引用 SightLoop 源码，SightLoop 也不打包 PinFix**。

## 闭环是怎么跑起来的

1. 开发者或测试在真实页面上用 PinFix 标注问题，采集元素锚点。
2. PinFix 通过 `POST /api/issues` 提交结构化锚点与问题描述。
3. SightLoop 建立会话：解析源码位置 → 召回历史知识 → 生成修复方案（PlanIR）→ 实施修改 → 执行校验命令。
4. 状态回传到页面：PinFix 在原元素位置显示问题卡片与进度标记。
5. 开发者可在页面上追加反馈、批准方案、确认或回撤；自动评审通过**不等于**人工确认。
6. 确认后修改落入工作区（PR 模式下尝试创建 PR），并把修复经验写入知识库。

对应的接口清单见 [SightLoop 接入指南](sightloop-integration.md)。

## 什么时候需要它

- **只用 PinFix**：你更信任自己的智能体会话，想让它拿到精确的定位信息后自行改码；或团队里还没有服务端基础设施。
- **PinFix + SightLoop**：希望问题从发现到验证、回滚、知识沉淀全自动闭环，并且需要多人审阅与审计。

## 安全前提

SightLoop 守护进程能修改注册项目中的文件，属于高权限工具：

- 本地服务优先绑定回环地址，注册项目限制在允许的根目录内，编辑范围受文件白名单约束。
- 使用最小权限、可撤销的令牌；不要在公开网页中嵌入通用凭据。
- 页面侧配置会暴露在页面脚本可读的位置，仅在信任的目标页面使用。

详见[安全政策](../SECURITY.md)和[SightLoop 接入指南](sightloop-integration.md)中的安全清单。
